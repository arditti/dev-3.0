Central WAKE / event-subscription mechanism

Agents subscribe to external events (GitHub, CI, deploys, timers) and get woken with structured envelopes — scoped to task, project, space, or everything.
Verdict Benefits Reference design What exists Gaps Design Extensibility Queueing Open source Plan Migration Risks

Verdict: build it — the hard half already exists

Everything external enters dev3 today by polling (merge checks every 60s, PR status every 5–15 min, three separate 30-second tick schedulers). There is no way for an agent to say "wake me when X happens" and go idle. Yet the consumer side of an event bus is already built: a per-task actor/mailbox state machine (dispatchLifecycleFinding is literally "external finding wakes a task"), one backend-neutral seam for typing a message into any agent's terminal (deliverAgentPrompt with quiet-pane hold), and an automations engine that can spawn fresh tasks. What is missing is a subscription registry with scopes, a router that decides who gets woken, and a wake path for tasks with no live pane.

Key strategic point: dev3's pane-typing delivery is harness-agnostic push. Claude Code itself has no local external-wake API (only cloud Routines and MCP Channels); Codex/Gemini have less. dev3 typing an envelope into the pane works identically for every agent CLI — dev3 can offer what no single harness offers.

Proposed design

A subscription record, a router, and reuse of every existing seam

The subscription record — one persisted object per "wake me when":

EventSubscription {
  id, createdBy: "agent" | "user" | "config",
  scope:  { kind: "task" | "project" | "space" | "global", id? },
  source: string,          // open vocabulary — built-ins and any custom emit source
  filter: Condition,       // generic predicate tree with and/or nesting, see below
  action: "deliver-to-agent" | "launch-task" | "notify" | "move-column",
  delivery: { mode: "immediate" | "debounce" | "digest",
              debounce?, schedule?, urgentBypass?: Condition },
  target: { taskId? | taskTemplate? },   // who wakes when it fires
  expiry: ttl / one-shot / until-task-ends
}

Filters are a generic condition tree, evaluated against the normalized event — never per-source flag lists, so a filter written today works on a source invented next month. Canonical form is a small JSON predicate tree; comparisons over numbers and strings, combinators nest arbitrarily:

Condition =
  | { all: Condition[] }          // AND
  | { any: Condition[] }          // OR
  | { not: Condition }
  | { path, op, value }           // leaf: path into {source, kind, key, payload.*}

ops: eq, ne, gt, gte, lt, lte    // numeric & string
     contains, startsWith, endsWith, glob, regex, in, exists

// "CI failed on main at least 3 times, or any deploy event went red"
{ any: [
  { all: [ { path: "source",           op: "eq",  value: "ci" },
           { path: "payload.branch",   op: "eq",  value: "main" },
           { path: "payload.attempts", op: "gte", value: 3 } ] },
  { all: [ { path: "source",           op: "eq",  value: "deploy" },
           { path: "payload.status",   op: "in",  value: ["failed","rolled-back"] } ] }
] }

On the CLI the same thing reads as one expression, parsed into the tree: dev3 subscribe ci-verdict --when 'payload.branch == "main" && payload.attempts >= 3'. The evaluator is a dependency-free pure function of (condition, event) — roughly 150 lines, exhaustively unit-testable, and shared by every provider, the router, and a dev3 subscribe test dry-run that replays recent events from the audit log against a candidate filter. Deliberately not a general scripting language (no CEL/jq dependency, no user code execution at filter time): comparisons and boolean nesting cover the actual patterns, and anything genuinely computational belongs in the woken agent, not the filter.

Storage: task-scoped subscriptions live on the Task record (the proven scheduledMessages pattern — dies with the task, survives restarts). Project/space/global ones live in a new, additive file under the existing data dir — no renames, no format changes to existing files, honoring the on-disk invariants.

Producers: generalize the activity pollers into an event engine keyed by what subscriptions exist — one shared per-repo GitHub poll serving every subscription on that repo, reusing the existing foreground/background throttling. Later: an authenticated /hooks/<token> route on the already-running remote-access server for true push (GitHub webhooks, deploy systems), and a file-watch source.

Delivery (the router): when an event fires, resolve the target in order — (1) live pane → wrap in a <dev3-event source="…" kind="…"> envelope (sibling of the existing cross-task message envelope) and deliver via deliverAgentPrompt with hold, so bursts coalesce into one turn; (2) task exists but pane is dead/hibernated → the new wake path: un-hibernate, relaunch the agent, queue the envelope as its first prompt; (3) no target task → spawn one via the automations path; (4) action is notify → existing notification fan-out. Every firing also lands in the append-only agent-traffic log and the board-events feed (its kind field was reserved for exactly this).

Agent-facing API — the full lifecycle, not just creation. Every operation available where subscriptions are created:

CommandDoes
dev3 subscribe <waker> [--scope …]Create; confirmation names the subscription id and the envelopes to expect (the screenshot UX).
dev3 subscribe list [--scope task|project|space|all]What is watching right now: id, waker, scope, filter, target, last fired, expiry. An agent (or the user) can always answer "what will wake me, and why".

Ships with a skill. dev3 already auto-installs its agent skill into every harness's config dir on startup; the event platform extends it (or adds a sibling dev3-events skill) so agents can configure the mechanism, not just consume it: how to define a custom waker for this project ("deployment" means something different per project — a CI job here, a dev3 event emit in a deploy script there, a health-endpoint command-poll elsewhere), how to write filter conditions, when to auto-subscribe (a task that just opened a PR subscribes to pr-activity; a task about a deploy pipeline registers the project's deploy-finished waker if missing — proposing it to the user when it belongs in .dev3/config.json), and the etiquette rules: transition-only firing, TTLs, unsubscribe when the reason is gone. The skill is what turns the platform into autonomous behavior — agents wire themselves to the right events per project instead of the user hand-configuring each one.

The scheduler control center — one component, four mounts. The UI surface is a single component that lives at every scope, pre-filtered to it: mounted on a task it shows that task's subscriptions; on a project, everything project-scoped plus a roll-up of its tasks; on a space, its projects; globally, everything. Same columns, same actions everywhere — only the scope filter differs, so learning it once is learning it everywhere (and it is one component to build and test, not four).

Placement note for implementation time: a new panel at four mounts is precisely a complexity-budget decision, so the concrete placement (drawer vs settings tab vs board surface) goes through the /ux-principal pass before any code — the design here fixes only the principle: one pre-filtered component, never four bespoke screens.

Extensibility — sources are providers, and the CLI is the universal one

GitHub is just the first provider; custom CLIs, timers, deploys, and anything scriptable plug in without touching the core

The bus core never knows about GitHub. Every source implements one small provider contract and emits the same normalized event; the registry, router, envelope, delivery, and audit log are shared and source-blind:

Dev3Event { source, kind, key, occurredAt, origin, payload }   // what every provider emits

EventSourceProvider {
  kind: string                       // "github-pr", "timer", "exec-poll", …
  accepts(subscription): boolean     // which subscriptions it serves
  start(subs, emit): stop()          // watch reality, call emit(event) on transitions
}

The waker store — built-ins listed, customs welcome

Subscriptions should not be raw JSON the user hand-assembles. A waker is a named, reusable definition — a provider plus its configuration, default filters, and a default action — and the waker store is the catalog that lists them: built-ins shipped by dev3 alongside customs the user defines. Subscribing then means picking a waker by name and scoping it: dev3 subscribe pr-activity, dev3 subscribe deploy-finished --scope project. The precedent is dev3's model catalog: dev3 owns the skeleton of the catalog, the user owns its contents, and a custom entry is a first-class citizen everywhere a built-in appears — the same list in the CLI, the UI picker, and the subscription record.

WakerKindDefined by
pr-activity, issue-opened, branch-moved, ci-verdictbuilt-in (GitHub provider)dev3
every / cron, file-changed, task-lifecyclebuilt-in (timer / file / board providers)dev3
deploy-finished — a deploy script ends with dev3 event emit --source deploy …custom (emit contract: reserves a source name + expected kinds)user / project config
staging-healthy — { command: "curl -sf …/health", interval: 2m, dedupe: output-hash }custom (command-poll definition)user / project config
sentry-alert — tokened webhook URL + payload mappingcustom (webhook, stage 3)user

Storage follows the scope: project-level custom wakers belong in .dev3/config.json so they travel with the repo and the team; personal ones in an app-level catalog file. Because a committed waker runs commands (command-poll) or triggers agent prompts, custom wakers from a branch must respect the same trust boundary as committed scripts — a foreign-code task ignores the branch's wakers exactly as it ignores its setupScript.

Two rules make this safe and honest. Provenance is stamped, never claimed: an emitted event carries origin: cli plus the emitting task id — a script cannot forge origin: github-poll, so a consumer can always tell first-party observations from third-party claims. Normalization is the contract: because every provider emits the same shape, filters (source/kind/key globs), transition dedupe, rate caps, TTLs, and the audit trail are written once and apply to a source that does not exist yet.

Queueing & decoupling — yes to a durable queue, no to Temporal

Producers and consumers must be decoupled; the machinery for it should be ~200 lines, not a workflow server

Decoupling is already the requirement behind the router: a producer emits a Dev3Event and returns; nothing about delivery (live pane? dead pane? spawn a task? notify?) leaks back into the provider. What must be added is durability between those two halves — a persisted pending-deliveries queue, because today the equivalent path silently drops (an agent message to a dead pane is discarded with a toast).

GuaranteeHowPrecedent already in dev3
At-least-once deliveryFiring appends a delivery record to a persisted queue; the record is removed only after deliverAgentPrompt reports delivered/held. App restart replays the queue.Task.scheduledMessages — persisted, 30s tick, offline late-fire catch-up ("fires late, never lost")
Dedupe / idempotencyEvery event carries a key; a subscription fires once per key transition, so a replay after a crash cannot double-wake an agent.computeSignalKey — the PR bell already rings only on transitions
Ordering per consumerDeliveries to one task drain through that task's FIFO; different tasks proceed in parallel.The per-task actor mailbox — this is exactly what it is for
Backpressure / coalescingMultiple pending events for one target collapse into one envelope at delivery time; per-subscription rate caps.The message-hold mechanism already batches a burst into one turn
Dead-letterAfter N failed delivery attempts, stop retrying, mark the subscription, raise attention to the human.Automations' missed/catch-up taxonomy with its grace window

Delivery policy — batching a chatty source into digests

When an event fires and when the agent wakes are two different decisions. Each subscription carries a delivery policy, so a chatty PR does not cost a model turn per comment:

ModeBehaviorFits
immediateDeliver on firing (the pane-quiet hold still coalesces a burst arriving together into one turn).CI verdicts, deploy results — the agent is waiting on it
debounceStart a quiet window on the first event; more events extend it; deliver one combined envelope when the source goes quiet (cap so it cannot be extended forever).Review sessions — a reviewer leaving 14 comments in 10 minutes becomes one wake with all 14
digestAccumulate everything and deliver one digest envelope on a schedule — hourly, daily at 9:00, or cron. The envelope carries the events grouped by kind with counts and the current end-state ("3 CI runs, final: green; 9 comments across 2 threads"), so the agent reasons about now, not each step."Check my PRs each morning", low-priority repos, project-wide activity feeds

Plus an urgentBypass condition — a filter-tree predicate evaluated per event that jumps the batch: digest mode on a PR with urgentBypass: payload.ci == "failed" means comments wait for the morning digest but a red build wakes the agent now. Digest scheduling rides the same timer provider as everything else, and a digest whose task pane is dead follows the normal wake path — one wake for the whole batch is exactly when waking a hibernated task is worth it.

Message semantics — the Kafka/SQS vocabulary, mapped local

Two stores with different jobs, both plain local files. The event log is Kafka-shaped: append-only, every firing recorded, consumers read by cursor — and dev3 already ships this shape (dev3 events is cursor-based by decision, its kind field reserved for growth; the agent-traffic log is append-only). The pending-deliveries queue is SQS-shaped: a message per (event × subscription target), acknowledged on delivery, retried with backoff, dead-lettered after N attempts.

Kafka/SQS conceptIn the bus
Durability / retentionEvent log persisted with a retention window (size- and age-capped, like the 50-note cap); the queue is persisted JSON replayed on boot.
Ack / delete-on-consumeA queue entry is removed only when deliverAgentPrompt reports delivered/held; anything else stays for retry.
Visibility timeoutAn entry being delivered is marked in-flight with a deadline; a crash mid-delivery makes it visible again next tick (idempotency keys stop a double-wake).
Message TTLPer-waker messageTtl: an undeliverable event expires instead of waking an agent with stale news — "CI passed" is noise a day later; expiry is logged, and expiry of the last delivery attempt can degrade to a human notification.
Dead-letter queueAfter N attempts the entry moves to a visible dead-letter list on the subscription; the subscription auto-pauses and raises attention.
Purge / cleardev3 subscribe clear <id> drops that subscription's pending deliveries (e.g., before waking a long-hibernated task into a flood); the task's "Watching" panel shows pending counts with a clear button.
Consumer groups / offsetsEach subscription is its own consumer with its own cursor into the log — one noisy subscriber never blocks another (per-task actor FIFOs give per-consumer ordering).

Why not Temporal (a durable-workflow engine: a server plus a database plus worker processes, giving replayable long-running workflows)? Wrong size in four independent ways. (1) Infrastructure: it needs a running server and datastore on the user's machine — and dev3's own update-channel rules say a brew dependency is not guaranteed present; this repo hand-rolled Web Push precisely to avoid one dependency. (2) Scale: Temporal is built for distributed fleets executing millions of workflows; dev3 is one local process handling at most tens of events a minute. (3) Fit: dev3 already has the two primitives Temporal would be imported for — a persisted queue pattern and per-entity serialized execution (the actor mailbox). (4) Portability: a required server dependency breaks the Windows and headless-remote stories. The same reasoning rules out embedded job-queue libraries (BullMQ needs Redis; pg-boss needs Postgres). Steal Temporal's semantics — at-least-once, idempotency keys, replay-on-boot, dead-letter, visibility — implemented on the house pattern: a persisted JSON queue plus the existing tick scheduler and actor mailbox. If dev3 ever becomes a multi-machine fleet product, revisit; the provider/router seams would survive that migration.

Migration impact — no data migration; subsystems absorbed one at a time

User data: nothing migrates. Every store is additive — a new field on Task older app versions simply ignore, a new sibling subscriptions file, a new SQLite queue file. No existing file changes format, nothing is renamed or moved, which is exactly what the on-disk invariants demand (every installed version shares ~/.dev3.0).

One deliberate non-goal: this is not the typed push-bus redesign for main→renderer messages (an approved but unimplemented sibling design). The WAKE bus targets agents and tasks; the push bus targets the UI. They should stay separate, with the WAKE bus emitting into pushMessage as one of its consumers.
